假如618大促 怎么设计线程池任务队列？

这是一个高并发场景，任务处理的时间不确定，要把保证系统的稳定性。

根据线程池的几个主要参数入手：

  1. 首先需要根据实际情况配置线程池的核心线程数，个数可以略小于实际并发数，留出一定的缓冲空间。另外是最大线程数，其一般为核心线程数的2-3倍。同时高并发事件并不是持续的，因此配置合理的存活时间可以避免内存的浪费，可以配置非核心线程的存活时间，一般根据活动高并发的持续时间来设定。

  2. 任务队列的选择，一般选择有界阻塞队列ArrayBlockingQueue，避免内存溢出，同时根据并发情况和任务丢失的容忍度选择合适的队列容量。（任务队列创建后无法修改，若想扩容则需要创建新的线程池，然后将任务逐步迁移到新的线程池中）

  3. 拒绝策略的配置也十分关键，一般对可靠性要求较高的系统，可以配置CallerRunsPolicy（交给发起的线程来完成）或者自定义实现任务重试。

  4. 另外可以配置线程池监控和动态线程池，实现系统状态监控和线程池的实时调整。

2025-04-08 Tue(周二)

实现了动态线程池中的任务队列扩容缩容，通过自定义阻塞队列实现。

线程池Executor中的阻塞队列的final修饰的，无法替换或者扩容，而常用的LinkedBlockingDeque和ArrayBlockingQueue并没有扩容方法，并且其中的容量、数组相关的对象也都是final修饰的，因此也都是不可变的。

若想实现动态扩容，那么就需要自己实现一个阻塞队列，令其容量可变，并给出外部调用的方法。

参照ArrayBlockingQueue的实现，这是一个循环数组实现的队列，需要注意队列操作的时候的并发安全，通过锁和条件变量实现。

关于阻塞队列：

在扩容之前，丢失的任务是不是找不回了，有没有什么策略？

任务丢失的典型场景

当队列满且触发扩容时：

  1. 扩容前的瞬间：新任务到达但被拒绝
  2. 扩容过程中：短暂窗口期内的任务可能丢失
  3. 扩容失败时：资源不足导致无法扩容

解决：多级降级队列（推荐）、拒绝策略+任务恢复、事务性任务提交
