7.记录用户抽奖结果

一整个抽奖过程先从活动账户额度充值、活动参与、抽奖执行【策略】，之后就是中奖记录写入和后续的发奖。本节要实现的是奖品记录写入和异步消息发送。
task 任务表：在写入奖品记录的时候，写入一条 task 消息发送任务，作为补偿使用。当 mq 发送失败的时候，则由任务扫描 task 消息进行发送。

发放奖品系统和抽奖系统通常是分开来的，为了保证MQ发放奖品接口的可靠性，需要在数据库中提供状态记录，实现任务补偿：

写入记录和发送 MQ 消息，不能用事务解决，事务主要是数据库事务，但 MQ 消息不是数据库事务。所以需要写入一个 task 表，通过任务补偿的方式进行处理。

  1. 首先实现用户中奖记录的入库

  2. 然后实现中奖记录消息的发送，以及任务的入库

  3. 最后实现一个Task来补偿处理失败的消息

    1. MQ没有事务，因此当MQ消息发送失败了就需要重发
    2. 创建一个定时任务，扫描任务表，将未成功的记录重新通过MQ发送
    3. Task不断扫描库表，MQ不断重发失败记录

奖品概率是如何装配的？

按照策略奖品中的概率，将最小的概率的小数位数去出，取到数，得到一个整数值，然后用所有的概率去乘以该整数值，得到每一个奖品需要装配的个数，将奖品存入集合后打乱，然后通过Map映射所有的奖品，类似于（1:106，2:107），最后将其存入缓存中。同时将之前的整数值也进行缓存，用于后续的随机值生成。

依据策略构建责任链、规则树的流程

责任链：通过策略获取需要装配的责任链，判断用户当前的奖池。依次是黑名单，积分权重和默认奖池的三个责任链的判断。

首先是黑名单，根据数据库中配置的黑名单用户id进行筛选，若在黑名单中，则直接返回黑名单积分奖励，反之进入下一个模块进行判断；

在积分权重的责任链中，首先根据抽奖策略，根据用户积分的规则生成奖池，例如4000积分可以抽哪些奖品，5000积分可以抽哪些奖品，并将奖池缓存到缓存中。若用户的积分达标，则选择对应的奖池进行抽奖，并返回奖品，反之进入默认奖池。

责任链的最后一个环节是默认奖池的抽奖，在默认奖池中进行抽奖，返回奖品。

‍

规则树：读取数据库中的规则树配置。规则树用于进一步对用户抽到的奖品进行过滤。首先是奖品规则节点，策略中对奖品中配置了规则，例如用户需要抽满10次才能解锁该奖品。在规则树的配置中，若用户不满足，走幸运奖的分支；若用户满足，则走库存校验节点；在库存校验节点中，若库存充足，则直接返回奖品，否则还是走幸运奖分支。

抽到一个奖后的流程？

抽到一个奖后，需要进行奖品库存的扣减、用户抽奖记录的创建、用户账户抽奖次数的扣减、用户奖品发放记录的创建。

扣减库存的流程？

在项目中是将库存信息预热到缓存中，先对缓存中的库存进行扣减，然后通过异步消息队列和RabbitMQ的订阅通知，实现对数据库库存的更新和清空。

超卖与少卖的问题？

业务中通过decr的原子操作对缓存中的库存进行修改，然后对库存的扣减加锁，这个锁保证了已扣减的库存不会被重复获取，保证了不会超卖。

中途需要增加库存怎么办？

项目中使用的是decr的方式对缓存中的库存进行扣减的，若有增加的需求，则应当使用incr的方式增加，同时上锁。

sku活动设计的思路？

sku的设计是为了实现更加灵活地配置活动、奖励次数、活动参数总次数，实现了用户参与活动获取抽奖次数的功能。

如何参与活动？

用户领取活动的过程类似于对商品下单的过程，需要对sku进行下单，获取对应的活动次数。获取的方式可以包括签到、活动奖励等。

线程池的应用？

在task任务库表扫描中使用了线程池，通过对数据库中任务表的定时扫描，实现发送奖品的消息能够成功发送。

  1. DDD的设计模式和设计理念与传统的SpringMVC的区别？
    回答：DDD主要是我们开始接到一个业务会先进行一个领域的划分，针对多个子领域每个子领域有自己的服务层，领域内需要用到的模块都在领域内去实现，同时DDD不像SpringMVC直接使用数据库表对应的PO对象作为业务对象来使用，他会在每个领域内定义自己需要的聚合对象，实体对象和值对象，同时如果有涉及对对象内属性有通用的处理逻辑，我们也可以直接在类中定义对应的处理方法，这样也不会影响到其他领域的编码。这样的话不会造成代码过多的冗余，修改起来比较方便，也比较易于扩展。
  2. 你说DDD扩展比较方便，为什么SpringMVC扩展不方便呢？
    回答：SpringMVC可以说是针对接口编程，针对每个接口我们要写对应的服务层，这个服务层的处理逻辑可能比较复杂，导致我们这个代码很冗余，然后使用DDD的话我们自己领域内的东西我们可以封装成一些类似于工具啊什么的，自己领域内的东西也不会影响其他领域。
  3. 什么叫领域？
    回答：比如我在这个项目中就是划分了四个领域，抽奖过程我划分到活动领域中，以这个举例就是用户参与抽奖的过程，用户点击参与抽奖，前置的一些条件判断，比如活动时间校验和参与活动次数检验，就是在活动领域的。策略领域就是负责抽奖的策略，活动领域只负责抽奖这个动作，具体怎么抽的不负责，由策略领域负责。还有奖品领域用来发放奖品，策略领域负责抽奖，抽奖完成后由奖品领域负责奖品的发放。然后还有一个返利领域，主要是用户做出一些行为，比如签到或者支付完成之后，会给用户增加一些抽奖次数，增加用户的活跃度，完成一个闭环。

    回答：活动领域就是从用户的角度出发，串联一下用户参与活动的这个流程，然后进行下一步的设计，比如用户点击抽奖，我们就进行一系列校验，如果校验通过就进入下一个策略领域进行抽奖。
  7. 以一个具体的例子帮我串联一下整个流程。
    回答：比如一个用户进来之后我们就先判断活动的有效期，再进行一个抽奖次数的校验并扣减，如果通过就记录一笔参与活动的记录，把这个记录传给策略领域，策略领域就知道了用户参与的是哪个活动，根据数据库表配置的奖品信息进行一个抽奖，抽奖完成之后写入一条中奖记录表，奖品领域根据中奖记录给用户发奖。最后还有一个返利领域，这个其实是为了用户能够参与活动的嘛，比如点击签到或者支付完成之后给用户增加抽奖次数。然后我再详细讲一下这个策略领域的具体实现吧，在策略领域我主要把抽奖这个动作划分为前中后三个阶段，抽奖前就是进行一些必要校验，在这里我设计了两种情况，第一种就是黑名单，可能有一些用户的行为不正常，他们抽奖的时候我们直接返回一个兜底奖品，这个奖品通常是比较廉价的，所以也不需要做库存扣减等动作，直接进行奖品方法，第二种情况是权重抽奖，就是说一个用户如果抽奖的累计积分已经到达了一定数量，我们会给他们一些比较好的奖品，不会抽中一些廉价奖品，我们也在这里进行一个处理，如果不符合前两个规则就走默认的抽奖流程，获得一个奖品ID，抽奖前的逻辑是采用责任链设计模式设计的，接下来是抽奖中的流程，是使用决策树的设计模式，首先根据获得的奖品ID，判断奖品有没有加次数锁，这里的次数锁是设计给某些价值比较高的奖品，避免用户一开始就抽中这些奖品，所以对奖品做一个次数锁限制，比如抽奖3次才可以解锁，在这里就可以判断一下用户中奖的ID如果加了次数锁，获取用户抽奖次数和次数锁的大小，如果不符合条件直接返回一个兜底奖品，符合条件或者奖品没有加次数锁，直接进入库存扣减的判断，如果库存充足，扣减库存并发放奖品，库存不足则返回兜底奖品，这里库存扣减的时候我选择将奖品库存提前预热到redis中，然后使用derc的原子操作对库存进行扣减，并使用setnx加锁操作进行兜底，保证库存不会重复扣减，在扣减完成之后将奖品ID放到延时队列中，通过定时任务读取延时队列来更新数据库中的库存值保证数据库和redis的一致性。在并发量很高的时候，库存可能很快被扣减为0，这里我使用了消息队列的方式，当库存被扣减为0之后，监听消息队列的消费者会将该奖品对应的延迟队列数据清空，然后直接更新数据库库存为0，保证了一致性，并且减少不必要的资源浪费。
  8. 活动领域怎么扩展，你的扩展思路是怎样的？
    回答：用户参与活动的时候可能还涉及一些其他的校验，不只是校验我们之前提到的活动时间和用户参与次数，这时候我们就可以继续加一个责任链节点的实现类，然后装配到责任链里面，比较方便的进行扩展。
  9. 策略领域是怎么串联活动领域的？
    回答：用户参与活动会生成一个活动参与记录，这个记录中就包含活动ID，这个记录传给策略领域，策略领域就可以根据活动ID查找对应配置的奖品信息，然后执行一个具体的抽奖操作。
  10. 那你的策略领域是怎么做扩展的呢？你的领域模型是怎么扩展的？
    回答：这个同样也是，以后抽奖的规则如果有什么变化，有一些新的想法，我们可以通过对原来责任链或者决策树节点的添加，然后重新装配进行一个策略的扩展。
  11. 责任链的设计模式是怎样的？
    回答：设计一个统一的接口，然后多个实现类去实现不同的处理逻辑，最后通过工厂对责任链进行一个装配，避免代码中出现比较多的ifelse语句。
  12. 责任链模式解决的什么问题？
    回答：解决代码中频繁的逻辑判断，代码复杂性比较高，不易扩展。
