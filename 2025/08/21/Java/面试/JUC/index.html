线程的创建方式？

  1. 继承Thread类，实现其中的run()方法，调用start()启动；
  2. 实现Runnable接口，实现其中的run()方法，通过Thread()的有参构造，创建出线程，然后调用start()方法启动；
  3. 实现Callable接口，实现其中的call方法，该方式下线程可以定义返回值，使用FutureTask对象接收返回的结果。最后通过Thread()的有参构造，创建出线程，然后调用start()方法启动；
  4. 线程池

线程状态及其切换？

NEW：新建状态，但是还没有调用start()方法。

RUNNABLE：调用start()，线程变为可运行状态（包括了运行状态、可运行状态和io阻塞状态（BIO），后两者其实都是在等待资源）

io阻塞状态为RUNNABLE？

由于 BIO 导致的线程阻塞，在 Java 里无法区分，仍然认为是可运行

BLOCKED：阻塞状态：获取锁失败，等待进入代码块。

WAITING：等待状态：Object.wait()、Object.join()、LockSupport.park()，等待唤醒。

TIMED_WAITING：计时等待：Thread.sleep()、Object.wait(long)、Thread.join()、LockSupport.parkUntil()、LockSupport.parkNanos()

TERMINATED：终结状态，线程执行完毕或者抛出了未捕获的异常

线程状态转换：

NEW –start()–> RUNNABLE
RUNNABLE –synchronized竞争锁失败–> BLOCKED
RUNNABLE –wait()/join()/park()–> WAITING
RUNNABLE –sleep()/wait(timeout)–> TIMED_WAITING
RUNNABLE –执行完毕/异常–> TERMINATED

BLOCKED –获取锁–> RUNNABLE
WAITING(未持有锁) –notify()/unpark()–> BLOCKED（竞争锁失败）或 RUNNABLE（成功）
TIMED_WAITING –超时–> RUNNABLE

当线程访问某个加锁资源失败时，需要等待锁的释放，因此进入阻塞状态，等获取到了锁，再变为可运行状态；

当线程调用了wait()，则线程进入等待状态，其他的线程调用notify()线程将尝试唤醒它，进入可运行状态。若未获取到Synchronized锁，则进入BLOCKED状态，若是Reentrantlock，则进入WAITING或者TIME_WAITING状态；

通过sleep()，线程将进入计时等待状态，待时间到了，进入可运行状态；

yield()与sleep()之间的区别

yield()后，线程放弃CPU，从Running状态转为Runnable状态，而sleep()是进入阻塞状态。

yield()后，所有的线程**重新竞争CPU**，因此该线程可能再次获得CPU，这是与sleep之间的一个区别。

yield()释放锁，而sleep()不释放锁。

总结：yield()释放锁并重新竞争锁，sleep()不释放锁，进入阻塞状态。

sleep()和wait()之间的区别？

所属不同、醒来时机方式不同、对锁的处理不同

  • 来源不同，sleep()是Thread类的，而wait()是Object类的；
  • ​wait(long)和sleep(long)都会自动醒来，但是wait()或者wait(0)不会，wait还可以通过notify()唤醒，都可以被打断，打断后抛出异常；
  • ​wait()方法的调用线程必须先获取到对象锁，而sleep不需要；
  • 锁对象调用wait()方法的线程**会释放该锁对象，在加锁的代码块中执行会释放代码块的锁**，允许其他线程获取对象锁；
  • 而sleep()如果在synchronized代码块中执行，并**不会释放对象锁；**

总结：二者的来源不同，一个是Thread，一个是Object；使用方式和唤醒方式有差别，可打断；wait()必须要先获取到锁，调用后释放锁；sleep()不需要获取锁，调用后不释放锁。

join()的作用？

让线程拥有执行的顺序，实现同步等待。

子线程调用join方法后，主线程进入WAITING或者TIMED_WAITING状态，当子线程执行完毕后，主线程被唤醒，进入RUNNABLE 状态，继续执行。

注意这里主线程​​wait(0);​​释放的是​当前代码块的锁，而主线程中原本的锁并不会释放。

总结：join()方法将一段代码块插入到主线程中执行，执行后会释放代码块上的Synchronized锁，然后等待线程结束后唤醒，继续执行主线程。

主线程：RUNNABLE -> start() 子线程 -> RUNNABLE -> join() -> WAITING
子线程：NEW -> RUNNABLE -> RUNNING -> TERMINATED（唤醒主线程,notifyAll()）
主线程：WAITING -> RUNNABLE -> 继续执行

存在的问题：join执行必须先获取子线程的对象锁。

  • ​​join()​ 必须获取子线程的对象锁，否则无法进入等待逻辑。

  • 主线程可能因锁竞争被阻塞，甚至导致死锁（如果子线程或其他线程长期占用锁）。

  • 最佳实践：

    1. 子线程避免操作自身锁。
    2. 使用超时机制。
    3. 优先用独立锁对象而非线程实例锁。

join(final long millis)可以传入一个时间参数，实现有时效的等待。

而Monitor锁中：Owner、EntryList、WaitList，是膨胀为重量级锁时使用的对象。

Monitor（重量级锁）在加锁的时候是怎么做的？

经过锁膨胀后，轻量级锁变为了重量锁，重量锁的加锁过程如下：

  • Java中每一个对象都可以​**关联一个Monitor对象，对象的Mark Word中记录指针指向对应的Monitor对象**。

  • 线程在获取对象锁的时候，其实是将线程交给了Monitor对象的管理。当Monitor中**onwer字段指向线程**​1后，线程1成功获取到锁；

  • 线程2、3此时想获取同一个对象锁的时候，会进入Monitor对象中的​EnterList​，变为​BLOCKED状态​，即等待锁的状态；

  • Monitor对象中的**WaitSet**中则保存获取过锁，但是不满足执行条件，进入​WAITING状态​的线程，即等待唤醒的状态；

  • 当线程1执行完成后，会进行锁的释放，此时**Monitor中的owner字段变为了null，唤醒EnterList中的线程，开始竞争锁**；

EntryList（ContentionList）和WaitSet之间的区别？

EntryList

  • 用于管理那些正在竞争锁的线程

  • 线程处于 BLOCKED 状态，等待锁释放时唤醒

  • 锁释放时，线程会被唤醒并尝试获取锁

EntryList中的线程是处于竞争状态的，是BLOCKED，会不断尝试获取锁

WaitSet

  • 用于管理那些主动放弃锁并等待通知的线程

  • 线程处于 WAITING 或 TIMED_WAITING 状态，**等待条件满足**后被 notify() 或 notifyAll() 唤醒

  • 被唤醒的线程会重新进入 ContentionList，尝试获取锁

二者中的线程在唤醒的时机和条件上存在区别：WaitSet 用于条件等待，锁释放并不一定意味着条件满足，因此需要显式通知。

轻量级锁的加锁过程？

当没有锁竞争产生的时候，线程使用的是轻量级锁，此时对象不会关联Monitor对象，而是使用自己的Mark Word来实现加锁。

当线程中执行到synchronized代码段的时候，会先创建出一个Lock Record，用于存储Mark Word和对象引用Object reference。Object reference会指向锁对象，然后使用CAS替换锁对象的Mark Word和Lock Record中的lock record值。

若cas失败，有两种情况：

  • 锁已经被抢占，此时发生了竞争，发生锁膨胀，对象关联Monitor对象，同时线程加入到EntryList，进入BLOCKED状态；Monitor中的owner指向占有锁的线程；
  • 若和占有锁的是同一个线程，则发生重入，会在线程中再创建一个锁记录，其中的指向为null；

释放锁的过程中，会查看锁记录中的Mark Word，若为null，表示是重入的，直接删除；若不为null，则先使用cas解锁：

  • 若解锁失败，则表明锁膨胀了，需要进入重量级锁的解锁；
  • 成功，则将Mark Word交换回对象锁中。
  • ​

总结：

偏向锁的Mark Word上保存**线程id**

轻量级锁的Mark Word上保存线程的​**锁记录**

重量级锁的Mark Word保存指向**Monitor的指针**

什么是自旋锁，重量级锁的优化有哪些？

自旋是重量级锁的一种优化方式，自旋会让线程发现锁被占用时先不放弃CPU，等待一段时间看是否有机会获取到锁。当自旋了一定的次数后还未获取到锁，则进入阻塞状态。

Java6之后有了**自适应自旋**，自适应自旋会根据上一次是否自旋成功来增加或者减少自旋的次数。

Java7之后，不能控制是否开启自旋功能。

自旋的实现原理是什么？

参考

自旋是通过循环CAS实现的，CAS通过读取-比较-修改的方式来对值进行更新，其中读取通过volatile保证操作的原子性，而比较和修改是原子操作。

再深入一点，CAS底层是靠调用 CPU 指令集的 cmpxchg 完成的，它是 x86 和 Intel 架构中的 compare and exchange 指令。它通过缓存锁的方式保证质量的原子性。

什么是偏向锁？

偏向锁是对轻量级锁的一种优化，它会再线程加锁前比较，如果锁对象中的线程id是当前这个线程，那么就不需要cas操作了，而是直接加锁。

但是当比较发现锁中记录的线程id不是当前线程，那么锁就会升级为轻量级锁。

偏向锁默认延迟：取消延迟：-XX:BiasedLockingStartupDelay=0​

偏向状态的撤销？

  • 计算哈希将会覆盖偏向状态位，导致偏向状态撤销，下次加锁就变为轻量级锁

  • 禁用偏向锁操作：-XX:-UseBiasedLocking，变为无锁

  • 其他线程使用该锁，变为轻量级锁

  • 调用wait() 和notify()，变为重量级锁（偏向锁不支持 wait() 和 notify() 方法）

批量重偏向？

某一个​**类​对象**对线程1撤销偏向超过20次后，下一次将会重新偏向另一个线程，而不会撤销。但是超过了40次，会不再偏向。

这么做的目的是为了减少偏向锁撤销带来的开销。

park unpark 原理

每个线程都有一个Parker变量，其中包含了_cond、_mutex、_counter三个部分，park和unpark操作都是以线程为单位的。

_cond用于保存当前的线程

_counter是一个标志位，当调用park的时候，若该标志位0，则线程会被放入_cond中，线程变为阻塞状态；若为1则线程不会被被阻塞，同时_counter值变为0；

调用unpark时会令_counter为1，同时若线程在_cond中，则会唤醒线程，并再次将标志位_counter变为0；若不在_cond中，即线程处于运行状态，则此时在下一次调用park的时候，线程不会阻塞。

不是很准确

park()和wait()、unpark()和notify()之间的区别

wait()和notify()必须配合Monitor对象使用，而park()和unpark()不需要；

park()和unpark()指定线程操作，而notify()是随机唤醒的；

park()和unpark()可以先unpark()，但是wait()和notify()不能先notify()；

wait()后线程会释放锁，但是park()不会，它只负责让线程阻塞；

可重入的实现？

对于重量级锁

通过锁状态的管理实现：

  • 当锁状态为0时，表示锁没有被占用，通过cas获取锁，替换对象头中的线程ID。
  • 当锁状态不是0，表示锁已被占用，若线程ID相同，且是可重入的锁，则将状态+1，然后获取锁，否则竞争失败后线程进入阻塞状态。

释放锁：

  • 可重入锁，线程退出对状态-1，当状态为0时释放锁。
  • 非可重入锁，线程退出直接释放锁。
轻量级锁

重入的线程其锁记录中的markword是null，则表明该锁是重入获得的，当不为null的时候，线程结束即释放锁。

线程池

为什么要用线程池？

线程池通过池化的方式管理多个线程，提高了线程管理的效率；线程池可以提高线程的复用性，提高响应速度，同时减少线程创建和销毁带来的开销；

如何创建线程池？

推荐自定义线程池，通过创建TreadPollExecutor对象来创建。

或者通过Executor框架的工具类Executors来创建，常见的有：

  • FixedThreadPool：线程数量固定，且不变。任务来了，有空闲线程则执行，否则加入到等待队列
  • SingleThreadPool：只有一个线程
  • CachedThreadPool：线程数量可调整的线程池，线程可以复用，线程不足时创建新的线程处理任务
  • ScheduledThreadPool：允许延迟执行或者定期执行任务

为什么不推荐使用？自定义可以实现资源可控，避免耗尽，上述4个工具类创建的线程池使用的队列长度都是Integer.MAX_VALUE，几乎是**无界队列了，大量堆积的请求会导致OOM；同时CachedThreadPool支持线程的创建，，这也会由于任务执行时间过长、数量多（大量的线程创建**）而导致资源的耗尽。

线程池参数有哪些？

maximumPoolSize：最大线程数、

corePoolSize：核心线程数

threadFactory：线程工厂

keepAliveTime：线程存活时间

unit：时间单位

workQueue：阻塞队列

handler：拒绝策略

线程池的核心线程会被回收吗？

为了减少创建销毁带来的开销，ThreadPoolExecutor默认不会回收核心线程，可以通过设置allowCoreThreadTimeOut(true)的方式让其回收。

核心线程空闲后处于什么状态？

一般处于阻塞状态WAITING，等待下一个任务到来后被唤醒。

非核心线程创建时都会设置线程的过期时间，当这个时间达到后，这些线程就会进入TERMINATED状态，并被移除线程池。

线程池的拒绝策略？/不允许丢弃任务，应该选择哪个拒绝策略？

深入了解ThreadPoolExecutor的拒绝策略

  • AbortPolicy：默认策略，拒绝任务并且抛出异常RejectedExecutionException​
  • CallerRunsPolicy：被拒绝的任务由调用者（主线程）自己执行完成，可以保证任务不会被丢弃，但是会降低新任务的提交效率。
  • DiscardPolicy：直接丢弃，不会抛异常。
  • DiscardOldestPolicy：替换并丢弃队列中最老的任务。

CallerRunsPolicy策略的问题？

主线程需要负责执行被丢弃的任务，如果任务耗时过长，则主线程中其他任务的提交会被阻塞很长的时间，影响程序运行。

CallerRunsPolicy采取的策略是当队列满了的时候，主线程自己执行，避免任务被丢弃；那么换一种思路，我们可以动态增加阻塞队列的大小来让其容纳更多的任务，从而保证所有任务都能被执行。也可以动态调整最大线程数，减少队列的积压。

常用的阻塞队列有哪些？

  • ArrayBlockingQueue：有界阻塞队列，无法扩容，一把锁实现，put和take之前都需要获取锁；

  • LinkedBlockingQueue：有界阻塞队列，默认容量为Integer.MAX_VALUE，约等于无界，使用两把锁，头结点出队和尾节点入队分别获取对应的锁；

  • DelayedWorkQueue：延迟队列，可以自动扩容，永远不会阻塞，队列中的任务按照延迟的时间来排序，采用的是堆结构；

  • SynchronousQueue：同步队列，没有容量，不存储元素，通过创建新线程的方式，将原本会阻塞的任务立刻执行。是CachedThreadPool使用的队列，最大线程数为Integer.MAX_VALUE。

  • LinkedTransferQueue：直接转移队列，支持生产者和消费者的直接传递，若任务到达后有消费者，那么调用transfer()方法直接交付，不用经过队列，否则退化为普通的队列实现。

线程池中的线程发生了异常后，是销毁还是复用？

两种提交任务到线程池的方法对发生异常的线程处理的方式不同：

使用execute() 时，未捕获异常导致线程终止，线程池创建新线程替代；

使用submit() 时，异常被封装在Future中，线程继续复用。

如何设定线程池的参数？

线程数太少：任务堆积，导致OOM。

线程数太多：大量线程同时运行，导致CPU的竞争，产生大量的上下文切换，影响效率。

较为简单的公式设定：

  • CPU密集型任务，设定线程数为核心数N+1，每个线程占用一个核运行，线程发生中断后CPU便空闲了，此时多出来的一个线程可以运行，充分利用CPU空闲时间。
  • I/O密集型任务，设定为2N，因为I/O操作不会占用CPU，在等待I/O的过程中，CPU就是空闲的，那么别的线程就可以使用，设置为2N可以增加CPU的利用率。

内存泄漏问题？
谁泄漏啊？

key为null的value无法被使用到，而导致内存泄漏，但是ThreadLocal在 操作之后会执行 清理key为null的Entry

设置key为弱引用的目的？

主要是在线程池中，线程被复用，其中的ThreadLocal若设置为强引用，则必须要手动回收旧的ThreadLocal，否则就会内存泄漏。而设置为弱引用，这些ThreadLocal会随着gc进行回收，同时也给程序一个判断依据：即key为null的value需要回收，进而避免了value的内存泄漏。

弱引用怎么防止不被GC？

貌似可以通过外部强引用的方式，让ThreadLocal不被回收。

InheritableThreadLocal

创建子线程的时候将父线程的threadLocals中的ThreadLocal对象复制给子线程的inheritableThreadLocals对象。

线程池使用中出现的问题

因为是创建时复制的，所以在线程池中使用时，由于子线程的复用，主线程无法通过设置InheritableThreadLocal来实现数据的共享。这个问题在使用链路追踪时会考虑到。
