什么是MVCC？实现原理？

ReadView中的4个重要字段：

  • creator_trx_id：表示事务创建者id
  • m_ids：表示未提交的活跃事务
  • min_trx_id：表示活跃的最小事务id
  • max_trx_id：表示活跃的最大事务id

聚簇索引记录中的两个隐藏列：

  • trx_id
  • roll_pointer：指向前一个操作前的旧数据（undo日志中，回滚用），称为版本链

MVCC基于版本链+ReadView来实现。

RC(读提交) 级别下：每次读操作都生成新的ReadView，能读到当前已经提交的事务的结果或者自己提交的结果；

RR(可重复读) 级别下：进入事务前创建的ReadView不变，读到的数据一直不变。

这两个隔离级别实现是通过「事务的 Read View 里的字段」和「记录中的两个隐藏列」的比对，来控制并发事务访问同一个记录时的行为，这就叫 MVCC（多版本并发控制）。

可重复读RR隔离级别是否可以解决幻读？

可重复读下隔离级别下，通过快照读和当前读的方式进一步避免幻读：

快照读：（select语句）这是通过MVCC的方式解决幻读，通过快照的方式记录事务开始前的数据状态，在事务中仅使用该快照进行操作，因此不会出现幻读；

当前读：（select for update等）通过next-key-lock解决幻读，首先是记录锁，避免了记录被修改，而间隙锁又保证了范围内不会被修改、插入、删除，因此在事务期间，这部分是锁定的，避免了幻读。

可重复读隔离级别可以很大程度上避免幻读的问题，但是仍然存在问题，例如在A事务查询一个不存在的记录后，B事务插入了该记录并且提交了，那么A事务之后修改了该记录就会提示修改成功，并且A事务之后的查询操作也可以查到该记录，出现了幻读。

因此可重复读隔离级别可以很大程度上解决幻读的问题，但是仍然无法避免。

如何最大程度避免？尽量在开启事务之后，马上执行 select … for update 这类当前读的语句，因为它会对记录加 next-key lock，从而避免其他事务插入一条新记录。

undo log、redo log、bin log

undo log：在每次修改操作前，会先记录原先的记录，然后用链表的方式与新数据串起来，也就是**版本链**，用于回滚，保证了sql的原子性。用于事务回滚和MVCC。

redo log：事务执行中，未提交的数据保存在Buffer Pool中，掉电后，该内存中的脏数据就会丢失。因此，MySQL会将每次修改记录增量更新到一个log文件中。InnoDB 引擎会在适当的时候，由后台线程将缓存在 Buffer Pool 的脏页刷新到磁盘里（Write-Ahead Logging，WAL技术）。实现了**事务提交后崩溃****恢复**​ ，保证事务的持久性。

数据库事务崩溃的两种情况：

  • 事务执行出错，使用undo log实现回滚；
  • 事务提交后，数据库就宕机了（Buffer Pool未刷盘，该事务丢失啦），使用redo log恢复；
  • 事务未提交就崩溃，那没办法，是无效事务；

​

bin log：主从复制、完整的数据库备份

redo log和bin log的区别：

  • 前者只保存部分，是循环写，写满后会覆盖之前的；后者不会覆盖
  • 进行的时机不一样
  • redo log保存的是当前在执行的事务，防止宕机导致提交的事务丢失，而bin log是完整的备份
  • 前者增量写入文件，适当时机刷盘，效率高，而后者会写入到特定cache中，然后异步写入磁盘

两阶段提交？

事务提交后，redo log 和 binlog 都要持久化到磁盘，需要保证它们都成功，否则会导致主从不一致问题。

redo log在事务执行的过程中不断写入，而binlog会在事务提交后写入，二者之间的执行存在时间上的差异，也就有可能出现不一致的问题。

两阶段指的是将redo log的写入分为两个步骤，prepare和commit，若MySQL用redolog恢复数据时，发现其处于prepare阶段，且没有对应的binlog，那么就会回滚该事务；反之若有，则无需回滚。

两阶段提交：在事务执行中，写入redo log，此时redo log处于prepare状态；

两阶段提交过程中发生崩溃的结果？

redo log处于prepare状态时，发生了宕机，此时事务还没有提交，丢失该事务，整体不会有一致性问题；

redo log处于commit状态时，发生了宕机，恢复后发现redo log还处于prepare状态，此时若能再binlog中找到对应事务的id，则不用回滚，反之则需要回滚。

总结：描述一下一个Update语句执行的完整流程

​UPDATE t_user SET name = 'xiaolin' WHERE id = 1;​

客户端先通过**连接器**建立连接

（Server层）

解析器（语法解析、预处理校验正确性、优化SQL） 通过词法分析识别出关键字，生成执行计划，**InnoDB将对应的记录所在的页读入到Buffer Pool**中，将记录返回给执行器

执行器会比较更新前后的记录是否一样，不一样则将更新前后的记录传给InnoDB层，让InnoDB真正的执行更新记录的操作

开启事务（引擎层）

记录下当前记录的状态，写入undo log，将该写入操作写入到redo log中

InnoDB层更新Buffer Pool中的记录，将其数据页标记为脏页，redo log中写入操作。这样就算完成了更新操作，后续会选择一个适当的时机将脏页写入到磁盘中（WAL技术）

将操作写入到bin cache中。

提交事务（两阶段提交），redo log的事务状态设置为prepare，然后将redo log刷新到硬盘中；从bin cache写入bin log（关键步骤，必须要成功）；然后引擎调用事务提交接口，继续写入redo log并设置其为commit状态，刷入到磁盘redo log中。

MySQL的查询流程

  • 客户端和MySQL建立连接，发送sql请求

  • sql经过**分析器解析语法、优化器选择索引，生成执行计划、最终通过执行器**调用InnoDB的函数接口。

    • 对于读操作，会先检查Buffer Pool中是否存在数据，若存在则直接读取，反之则从磁盘中读取，并放入到Buffer Pool中；这里还有一个自适应哈希索引，用于保存热点Key，加快查询的速度；
    • 对于写操作，先将数据写入Buffer Pool，并写入undo log中，然后将数据写入到Redo log Buffer（周期性写入到磁盘上的redo log文件）中；此外还有辅助索引的更新操作，索引的修改会先缓存到Change Buffer中，当相关索引页被读取时，再进行实际的更新操作（从而减少磁盘IO，提高写入的性能）；
    • 上述操作中所有的变更都会被记录到binlog中。

redo log的刷盘时机？

本身会调用后台线程将redo log buffer（数据库缓存区）中的内容写入到page cache（文件缓存区）中，然后调用 fsync 刷盘。

此外提供了三种刷盘机制：

  • 0：事务提交的时候不刷盘，每隔一秒从redo log buffer中写入redolog文件和磁盘。
  • 1：事务提交后直接写入redolog文件，并刷盘。
  • 2：事务提交后直接写入redolog文件，然后异步刷入磁盘。

​

binlog的刷盘时机？

会先存入到bin log buffer中，然后在**事务提交的时候写入到磁盘**。提交的磁盘的过程又可能会先存入到文件缓存区（page cache），然后后台线程等待时机磁盘；也可能事务提交就直接写入磁盘。

语法：explain sql语句;

关键字段：

  • type：查询的执行方式，all表示未使用索引全表查询、index表示遍历了​整棵索引树（索引覆盖） 、range表示对索引列进行​范围查询、ref非唯一索引查询、eq_ref主键索引查询或者唯一索引查询、const主键索引查询、system表示精准查询。

  • key_len：可以看出使用的索引的长度，判断联合索引中生效情况
  • extra：额外的信息，使用覆盖索引（Using index）、索引下推（Using index condition）、普通条件查询（Using where，没有回表）

什么是索引？底层结构是什么？

索引是用于数据库查找的工具，可以提升查询效率，减少全表扫描。

MySQL的InnoDB引擎采用的B+树的数据结构来存储索引：

  • 阶数更多，路径更短；
  • 磁盘读写代价更低，非叶子节点只存储指针，叶子结点存储数据；
  • B+树是一个双向链表，便于扫库和区间查询；

‍

一级索引和二级索引的查询流程？

又称为聚簇索引和非聚簇索引。

聚簇索引必须存在，而且只有一个，它的规则如下：

  • 没有指定索引，但存在主键，那么设定的主键就是聚簇索引
  • 没有指定索引，且不存在主键，则使用第一个不包含null的唯一（unique）索引作为聚簇索引
  • 上述均没有，则会自动生成一个rowid作为隐藏的聚簇索引

索引的存储也是使用B+树，对于聚簇索引，其叶子结点保存了行数据；而二级索引的叶子节点保存的是聚簇索引值。

什么是回表？

当二级索引的结果不满足查询结果，则会先通过二级索引得到主键值，然后到聚簇索引（主键索引）中查找整行的数据，这个过程就是回表。

‍

什么是覆盖索引？

指查询使用了索引，并且需要返回的列在该索引中能够全部找到。（避免使用select *）

反之需要进行回表操作。

什么是联合索引？

多个字段共同构成索引，需要考虑到索引失效条件中的最左匹配原则。

对于下面的sql语句需要注意：

​SELECT * from user where name like '陈%' and age=20，其中name和age字段创建了联合索引。

联合索引的范围查询失效？

MySQL5.6以前，只有name字段会用到索引，也就是说引擎层只会根据索引name来筛选，得到所有满足'陈%'的数据，然后进一步进行回表查询，获取到完整的数据，交给Server层筛选​​age=20​​条件的数据。

而5.6以后，有了索引下推的功能，引擎层中可以根据索引和失效索引（一般就是联合索引了）的条件提前对数据进行过滤，也就是说可以直接根据where name like '陈%' and age=20找出对应的数据，减少了引擎层中的回表次数，同时减少了向Server层传输的数据。

‍

最左匹配原则是什么？

最左匹配会一直向右匹配，直到遇到了范围查询(>、<、左匹配like)为止（该条件也会用到索引的），而<=、>=、between以及前缀匹配like的范围查询不会停止匹配（用于减少二级索引扫描的范围）。

但是对于in和=查询条件，索引的中的顺序可以改变，优化器会帮忙调整。

什么情况下索引会失效？

  1. 联合索引不遵循最左匹配原则，但是MySQL会自动排序
  2. 对索引使用了函数、表达式计算
  3. 左右/左模糊查询
  4. 字符串索引，查询未加单引号，出现了类型转换
  5. OR条件中，一个是索引，另一个不是索引的情况—–解决办法：将它们都设置为索引
  6. 不包含（<、>）的范围条件之后的索引会失效
  7. 子查询导致外部查询的索引失效（where id = (子查询)会变为 where exists (查询)），可以使用连接查询替换。

如果有索引 联合索引（a，b，c），查询 a=1 AND c=1会走索引么？c=1 呢？b=1 AND c=1呢？

​a=1 AND c=1会走索引，匹配a而过滤c，c=1和b=1 AND c=1都不会走索引。

什么是索引下推？

索引下推允许数据库在存储引擎层​直接利用​索引​和​失效索引进行​过滤数据，而不是将所有数据返回给服务器层再进行过滤。这样可以减少不必要的数据读取（减少回表次数）和传输，提升查询效率。

提前过滤的操作包括了对使用了函数的条件字段进行提前计算，并过滤数据，减小了索引失效带来的问题。

同时对于范围查询，提前过滤可以减少大量的不必要的数据的传输。

什么是唯一索引？

唯一索引的属性列不能出现重复的数据，但是允许数据为 NULL，一张表允许创建多个唯一索引。 建立唯一索引的目的大部分时候都是为了该属性列的数据的唯一性，而不是为了查询效率。

什么是前缀索引？

前缀索引：对文本的前几个字符创建索引，创建的**索引占用更小**，因为只取前几个字符。用于定位主键的位置，是二级索引。

MySQL深分页问题

实战！聊聊如何解决MySQL深分页问题

问题描述

深分页问题指的是在MySQL查询过程中，由于分页的**起始位置特别大，数据库在处理的时候需要从0开始一直扫描到查询的起始位置**，从而造成查询效率的下降。

问题分析

若查询用到了索引覆盖，那么相对好一点。但是一旦涉及到非索引字段的查询，那么就会产生回表，也就是需要重新将0到查询起始位置的数据都查询出来，这就会导致效率进一步下降。

优化
  • 子查询中预查询出id/连接查询（延迟关联）

思路：二级索引上查询获取主键id，然后在主键索引上直接查找

1.子查询优化：将深分页放到子查询中，子查询使用索引覆盖的查询，先查询出id，通过，最后返回这些id在主查询中查询出结果；

2.子查询中设定深分页的起始位置作为查询条件，可以让索引来快速找到起始位置。——若中间删除掉了数据，那么查询的结果会变，页面会出现重复，例如程序中默认设定起始页为100递增，那么某一页删除了5条数据，那么那一页在查询的时候就会查询到后一页的5条数据，出现重复。

  • 预存id

3.记录上一个查询的最大id—–只能一页一页跳转，否则获取不到最大id

4.范围已知则使用between…and替换limit

其中2、3、4方法都需要保证查询的id必须是自增的，uuid就不可以。

此外还可以使用分库分表的方式、使用ES等高效率查询引擎、业务调整来限制查询

总结

MySQL深分页问题可以通过子查询提前过滤、利用索引定位起始位置、使用betweenand替换、使用分库分表、使用搜索引擎、业务限制来解决。

实际业务中并不需要显示全部的数据，展示部分即可，例如限定用户只能翻100页，每页60条的话也就6000条。

水平分库：把同一个表的数据按一定规则拆到不同的数据库中，每个库可以放在不同的服务器上。

  • 水平分库，将一个库的数据拆分到多个库中，解决海量数据存储和高并发的问题
  • 水平分表，解决单表存储和性能问题
  • 垂直分库，根据业务进行拆分，高并发下提高磁盘IO和网络连接数
  • 垂直分表，冷热数据分离，多表互不影响

组件：sharding-shere、mycat

为什么需要分表、分库？

分表：当单表的中的数据达到一定量后，数据库性能会下降，这主要是由于MySQL基于B-Tree的索引结构的高度会随着数据量的增加而增加，数据的扫描IO就会增加，响应时间增加；

分库：在分布式环境下，主从之间需要数据同步，若不进行分库，那么会对整个数据库进行同步，而写入操作的非常昂贵的，因此需要进行分库，减少同步的数据量。

中间件方案：分库分表后，需要对数据的操作进行路由分发和再处理。

数据结构

为什么不用AVL树和红黑树？

AVL是平衡树，其约束条件多，，当数据库发生修改时，需要较多的节点调整来保持平衡，执行效率低；而红黑树约束相对较低，这导致它的高度会变高，从而导致查询效率降低。

此外最大的问题在于范围读取的效率，二者每次只能读取一个节点的数据，然后重新查找下一个目标。

B树和B+树，为什么使用B+树？

首先B树的所有节点都存放的是实际的数据，而B+树只有叶子节点存放实际数据，并且叶子结点之间使用双向链表链接；

B+树的查询结果都在叶子节点，相较于B树来说，其查询更加稳定；

B+树的范围查找更加高效，对链表进行遍历即可，B数需要先找到下限然后中序遍历找到上限。

因此，B+树相较于B树拥有更少的I/O次数、更稳定的查询效率，并且适合范围查询的优势。

外部

存储引擎有哪些，区别？

MyISAM引擎，索引使用的是B+树，在查询的时候，若指定的Key存在，无论是主键索引还是辅助索引，直接取出其data域的值，使用data域的值为地址即可从key_buff中读取相应的数据记录；（非聚簇索引，索引和数据分开存储，索引的结果是数据的地址，需要以此找到数据）

InnoDB引擎，索引使用的也是B+树，但是数据和索引存储在了一起，找到了索引也就找到了数据，另外辅助索引的结果是主键索引，因此还需要通过主键索引得到对应的数据。（聚簇索引）

索引总结：聚簇索引适合范围查找，而非聚簇索引在范围查找的时候需要频繁将查询到的地址对数据进行读取。因为聚簇索引的叶子结点按页存放，索引顺序和数据的物理顺序一致，范围查询只需要**少量的I/O操作（读取页）** ；而非聚簇索引拿到的是数据的物理地址，然后逐个去内存查找，会出现**大量的随机I/O**。

感觉这是主键索引（聚簇索引）的字段有一些额外的约束了。辅助索引中的字段可能分散在不同的数据页中，而主键索引的字段要求顺序存储（页）

外连接：

  • 取a表全部，并拼接与b表的交集部分，left join

  • 取a表独立的部分，left join on a.id = b.id where b.id = null​

  • 取b表全部，并拼接与a表的交集部分，right join

  • 取b表独立的部分，right join on a.id = b.id where a.id = null

  • 取a和b的并集，left join union right join，union会去除拼接后重复的字段

  • 选出不重复的记录数量，即ab的交集的对于ab的并集的补集，left join + is null union right join+is null

  • 交叉连接，cross join，取笛卡尔积
