HTTP的字段

HTTP缓存技术

存在缓存，则存在Cache-Control字段

强制缓存，完全根据Cache-Control来判断

协商缓存，缓存失效的时候生效：

  • 首先判断有没有Etag，若有，则将请求中的If-None-Match值设置为Etag发起请求

  • 若没有Etag，则判断有没有Last-Modified，若有，则将请求中的If-Modified-Since设置为Last-Modified

  • 服务器判断是否需要发送新的数据

    • 200：请求服务器
    • 304：读取缓存

HTTP/1.1

简单易于扩充，但是无状态、明文传输—不安全

长连接、允许管道通信、对头阻塞问题（服务器可能会长时间阻塞在第一个请求上）

存在的问题
  • Header不会压缩，只压缩Body；
  • 首部冗长、带来开销；
  • 队头阻塞问题
  • 没有请求优先级控制
  • 服务器只能被动响应

HTTPS

SSL/TSL安全协议

在原来的TCP和HTTP之间增加了一层SSL/TSL安全协议

实现了：

  • 信息加密：混合加密算法，实现连接阶段，使用非对称密钥交换；信息传输阶段，使用对称加密；

  • 校验机制：摘要算法（数据的哈希，私钥加密），用于校验数据的完整性；

  • 身份校验：CA数字证书，防止服务器公钥被冒充；（服务器将其公钥注册到权威机构，客户端在连接阶段会根据服务端发来的数字证书，使用权威的公钥进行解密和校验）

SSL/TSL中，使用四次握手，前三次得到服务器和客户端的**三个随机数字，并协商加密算法，基于这些随机数字和协商的算法得到会话秘钥**。

在双方最后一次握手中还会对之前的连接信息进行**摘要**，确保握手过程中信息没有被篡改。

SSL/TSL 1.2需要4次握手，而SSL/TSL 1.3只需要三次握手

客户端校验证书的过程

CA机构将服务端的公钥、用途、有效时间等信息进行打包，然后计算得到Hash值，使用**CA私钥加密**该hash值，生成签名。最终服务器得到一个包含hash值和签名的数字证书；

客户端在获取到证书后，使用**CA的公钥**对签名进行解密，将得到的哈希值与证书上的对比，若相同，则说明证书是可信的，服务器的公钥可用。

HTTP/2

改进
  • 头部压缩，同时发生多个请求头相同的请求，那么会消除重复部分
  • 二进制格式，由报文变为了二进制
  • 并发传输，解决队头阻塞问题，使用Stream ID区分不同的消息
  • 服务器主动推送资源
缺点

TCP接收数据的时候存在阻塞，必须等到完整的数据到来才可以读取，否则要一直等待该数据就绪（丢包等待重传），后续的数据即使就绪了也无法读取。

HTTP/3

将TCP协议改为UDP，解决HTTP/2中的队头阻塞问题。

  • 解决队头阻塞

**UDP**通过QUIC协议实现类似TCP的可靠传输，同样用StreamID的机制，但是丢包只会阻塞对应的流。

  • 更快速的连接

TCP

TCP三次握手、四次挥手

TCP可靠？

  1. 三次握手四次挥手：连接建立和关闭

  2. 序列号：防止丢失，避免重复

  3. 确认应答：确认接收情况

  4. 超时重传：发出去数据包，超时时间内未收到确认，则进行重传；接收到重复的数据包，表明发送的ack包丢失，进行重传。

  5. 流量控制：对发送方的数据流量进行控制

拥塞控制：

TCP报文头中窗口的大小是由接收方和发送发的拥塞控制窗口共同决定，但是其大小不会超过接收方的接受窗口大小。窗口大小=min｛接收窗口rwnd，拥塞窗口cwnd｝

根据超时重传机制，判断网络状况，选择不同的拥塞控制策略，对网络中发送方的数据包发送数量进行限制

  1. 慢启动算法：当发送方每收到一个 ACK，拥塞窗口 cwnd 的大小就会加 1。

  2. 当拥塞窗口 cwnd 「超过」慢启动门限 ssthresh，使用拥塞避免算法：每当收到一个 ACK 时，cwnd 增加 1/cwnd。

  3. 当触发了重传机制，也就进入了「拥塞发生算法」：

    1. 超时重传的拥塞发生算法：ssthresh 设为 cwnd/2，恢复为 cwnd 初始化值

    2. 快速重传的拥塞发生算法：cwnd = cwnd/2 ，也就是设置为原来的一半；ssthresh = cwnd；进入快速恢复算法

      1. 快速恢复

为什么需要timewait？
  1. 确保旧连接中的报文全部失效
  2. 确保被关闭的一方正常被关闭
服务端出现大量的timewait有哪些原因?
  1. 没有使用长连接（用的是短连接，keep-alive）
  2. 长连接超时（多个长连接建立后，服务器长时间没有收到请求，导致了连接断开，可能是服务器端的网络问题）
  3. 长连接的请求数量达到上限
