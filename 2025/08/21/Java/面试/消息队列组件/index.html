Redis消息队列

list结构

基本实现

使用链表模拟队列实现一个消息队列：LPUSH和RPOP相关命令分别实现入队和出队。

LPUSH和RPOP不会阻塞，当队列为空回返回Null，需要使用BLPUSH和BRPOP来实现阻塞等待。

优缺点

优点：

  • 利用Redis存储，不受限于JVM内存上限；
  • 基于Redis的持久化机制，数据安全性有保证；
  • 可以满足消息的有序性；

缺点：

  • 无法避免**消息丢失–消息被取出就没了**；
  • 只支持单消费者–不支持消息的重复消费；

‍

PubSub

Redis2.0版本引入的消息传递模型，消费者可以订阅一个或者多个**channel**，生产者向对应的channel发送消息后，所有的相关订阅者都可以收到消息。

基本实现

  • SUBSCRIBE channel [channel] ：订阅一个或者多个频道；
  • PUBLISH channel msg：向一个频道发送消息；
  • PSUBSCRIBE pattern [pattern] ：订阅格式匹配的频道；

pattern一共有三种：

  • h?llo：至多匹配1个任意单个字符；
  • h*llo：至少匹配0个任意相同的字符；
  • h[ea]llo：指定可以匹配的单个字符；

优缺点

优点：采用发布订阅模式，支持多生产、多消费

缺点：

  • 不支持数据持久化；
  • 不能避免消息丢失（发送未被订阅的频道，消息直接丢失）；
  • 消息堆积有上限（消息堆积在消费者），超出后消息丢失；

Stream

Redis5.0引入的**新数据类型**，实现了完善的消息队列功能。

基本实现

  • 发送消息的命令：XADD

​XADD users * name jack age 21：创建名为 users 的队列，并向其中发送一个消息，内容为{ name=jack, age=21 }，并使用Redis自动生成ID。返回ID。

  • 读取消息命令：XREAD

一条消息可以被多个队列重复读取，消息不会被删除，永久存在。

读取第0条数据：XREAD COUNT 1 STREAMS s1 0​

读取最新的消息：XREAD COUNT 1 [BLOCK 0] STREAMS s1 $​

XREAD命令的优缺点

优点：

  • 消息可以回溯–读完消息不丢失；
  • 一个消息可以被多个消费者读取；
  • 可以阻塞读取；

缺点：

  • 有消息漏读的风险–处理消息期间来的消息会漏读；

消费者组模式

特点

将多个消费者划分到一个组中，监听同一个队列（类似于线程池）。当前组中的消费者都是处理相同队列的消息，不同的组处理不同队列的消息。具备下列特点：

  • 消息分流：消息不是重复消费，而是**同组竞争消费，从而加快消息的处理速度**；
  • 消息标示：记录最后一个被处理的消息，这样即使消费者宕机，也可以根据标示找到读取的位置。保证每一条消息都会被消费；
  • 消息确认：消费中的消息处于​**pending状态，并存入一个pending-list**。处理完成后需要通过XACK来​**确认消息**，标记消息为已处理，并从pending-list中移除。pending的消息最终都会被消费；

优缺点

  • 消息可回溯—持久化；

  • 可以多消费者争抢消息，加快消费速度；

  • 可以阻塞读取；

  • 消息标记，没有漏读的风险；

  • 有消息确认机制，保证消费者获取的消息都会被消费（每一个消费者都有一个pending-list）；

考虑幂等的方式解决，例如分布式锁、数据库锁
