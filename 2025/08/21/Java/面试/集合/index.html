ArrayList

动态数组

扩容：创建出一个**比原数组容量大一半**的空数组，然后将原数组中的元素复制到新数组中，最后将原数组引用指向新数组。

​add(int index, E obj)：该方法需要对size和index进行比较，​size >= index​时才可以。而这个size需要注意的是，设置容量的构造函数中并不会修改size，它指向的是下一个插入的位置，即集合中元素的个数。在源码中，会将index之后的元素向后移动，可能会涉及到扩容。

所有和index相关的操作，例如在指定位置插入、设置值、删除值，都需要对index和size进行校验，不允许在超过size的位置上的操作。

JDK8的扩容：

首先是构造函数，包括了有参和无参的，其中无参构造得到的集合是一个空数组，在添加第一个数的时候会触发扩容。

扩容调用了ensureCapacityInternal()方法，其中调用了calculateCapacity()方法来获取当前需要的数组容量，传入ensureExplicitCapacity()方法进行扩容。

最终的扩容通过grow()方法实现，其中包括了几个关键点：

  • 通过位运算实现对旧数组容量扩容1.5倍：int newCapacity = oldCapacity + (oldCapacity >> 1);​
  • 若扩容后仍然不能满足，则会直接使用minCapacity作为容量；
  • 通过数组复制的方式，得到扩容后的数组；
ensureCapacity 方法

实现提前预分配空间，减少了重复扩容带来多次元素移动的问题，可以提高性能。

线程安全：

  • Collections类的synchronizedList方法

  • CopyOnWriteArrayList（互斥锁ReentrantLock，在写数据的时候会复制一份，然后再副本上进行写，原数组还可以用于读，存在读滞后的问题）

  • Vector类

LinkedList

双向链表

遍历：for、foreach（不支持遍历过程中修改）、迭代器（修改操作需要使用iterator中的方法）

线程安全方案：不是线程安全的，可以通过Collections来转化

获取元素：

无论是插入、删除还是添加，都需要先获取到对应位置上的node

细节：有三种获取，分别是首、尾、任意位置获取，获取前会先判断当前的位置是在前半段还是后半段，从而决定从首还是尾开始遍历。

LinkedList和ArrayList中toArray()方法的区别？

LinkedList通过遍历逐个赋值的方式实现，而ArrayList通过System.arraycopy()和Arrays.copyOf()方法实现。

​public <T> T[] toArray(T[] a){}方法，若数组a的大小小于size，则会返回一个当前数组的副本；若a的大小大于size，则会将当前数组复制到a上，并返回a。因此最可靠的做法就是接收该方法的返回。

HashMap

数据结构—散列表

1.8：首先通过对key进行哈希计算，得到hashcode，然后在数组上找到对应的位置：

  • 在获取时，找到该位置上的链表或者红黑树中找到key，然后获取对应的值（若不存在则返回null）
  • 在存储时，先在链表或者红黑树种查找是否存储过该key，若存在则覆盖，反之将该key-value存储到链表或者红黑树中

1.7：采用的是数组+链表的方式实现的

链表->红黑树：当put一个key-value后，链表的长度大于8的时候，会判断数组的大小，若大于64，则会将链表转换为红黑树。

1.8中的put()与resize()扩容

在put()执行之前和之后都可能会进行扩容

扩容的情况分为初始化扩容和超出阈值的扩容。

  • put之前（初始化），哈希表为空的时候，进行扩容（扩容为默认大小16）

  • put之后，根据负载因子（0.75）得到的阈值，判断当前哈希表的容量情况，若超过阈值，则进行扩容：

    • 创建一个新的两倍大小的数组；
    • 若是节点红黑树，拆分后节点个数小于6个时，则会变回链表；
    • 若是链表，则可能需要拆分：将旧数据的key重新计算哈希，每一个桶内的元素的哈希值与旧容量大小的与运算(e.hash & oldCap) == 0得到结果，若为0则newTab[j] = loHead;则位置不变，为1则newTab[j + oldCap] = hiHead;则移动到扩容的位置。通过该方式将所有的元素分配到新数组中（&代替取模运算）
    • 最后将元素进行插入，若没有冲突，即单个节点，则直接重新计算哈希后放入对应的位置，反之需要插入红黑树或者链表；

寻址算法

计算哈希

二次哈希，添加扰动，实现均匀分布：(h = key.hashCode()) ^ (h >>> 16)；

为什么HashMap的数组长度一定是2的次幂？

length的长度是2^n，使用与运算&代替模运算，提高效率。

因为除以2^n相当于向右移动n位，被移除的n位就是余数，所以与上2^n - 1即为余数。

在扩容中，可以实现快速判断元素是否需要移动：

​e.hash & oldCap == e.hash % oldCap，仅当oldCap为2^n才成立。

在计算位置的时候，可以实现位运算加速：

​(2^n - 1) & hash，得到在哈希数组上的位置。

是否支持key为null，value为null？

支持

线程安全吗？

不安全

  • JDK 1.7 HashMap 采用数组 + 链表的数据结构，多线程背景下，在数组扩容的时候使用头插法，链表的顺序会改变，存在 Entry 链死循环和数据丢失问题。
  • JDK 1.8 HashMap 采用数组 + 链表 + 红黑二叉树的数据结构，优化了 1.7 中数组扩容的方案，采用尾插法，解决了 Entry 链死循环和数据丢失问题。但是多线程背景下，put 方法存在数据覆盖的问题。

HashTable

线程安全，使用synchronized实现的加锁，但是是对整张哈希表进行的，因此并发性不高。

ConcurrentHashMap

JDK1.7

JDK1.7之前使用的是分段锁Segment实现的，Segment是一个继承自reentrantlock的可重入锁，总体看是一个二维数组，默认大小为16，将哈希桶HashEntry分成多个组，组可以进行扩容，每一个组使用一个可重入的锁，在对一个组进行写操作的时候，需要加锁，此时可以对其他的组进行读写操作。但是此时的哈希表的实现还是数组+链表的形式，因此存储效率不高。

分段锁的细节：

分段锁加在每一个Segment数组，该数组不能扩容，默认大小为16，即16线程并发。

根据Segment单个节点的容量和负载因子创建一个HashEntry数组。HashEntry默认大小为2，负载因子为0.75。

JDK1.8​

JDK1.8之后使用的node+CAS+synchronized实现，在每个node上，也就是每个哈希桶上，这样的锁更加细致，并发性更高。并且使用自旋锁，进一步提高并发性。同时哈希表优化为了数组+链表+红黑树的形式，提高了存储效率。

ConcurrentHashMap具有较好的并发性能，同时保证了多线程下的安全性。

为什么1.8不使用reentrantlock？
  1. 减少内存开销

若使用Reentrantlock，则每个节点都需要继承AQS来获得同步支持，但是并不是所有的节点都需要，只有链表的头结点（红黑树的根节点）需要同步，这会带来大量的内存浪费。

  1. JVM对synchronized的优化

首先synchronized的锁是JVM直接支持的，在JVM运行时会采取：锁膨胀、锁粗化、锁消除、自适应自旋等操作。而Reentrantlock获取锁失败后可能会直接挂起，产生上下文切换的开销。因此使用synchronized可以有效降低锁的竞争和线程挂起带来的开销，性能更高，并发性更好。
