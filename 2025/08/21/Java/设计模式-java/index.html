1.2关系的表示

关联关系

使用实线的箭头表示—>，一般表示对变量或静态方法的引用，表现为一种外在的关系。

聚合关系

使用空心菱形为起点，实线箭头结束（整体指向部分）。表示整体和部分的关系，但是二者可以分开，例如公司和员工、学校和老师，即是has-a的关系。

组合关系

使用实心菱形为起点，实线箭头结束。表示整体和部分的关系，但是二者不可以分割，整体消失，部分也就不存在了，例如头和嘴巴、公司和部门。

继承/泛化关系

使用带空心三角的实线表示，三角指向父类。这是代码之间耦合度最大的一种关系，是is-a的关系。

实现关系

实现关系使用带空心三角箭头的虚线来表示，箭头从实现类指向接口。实现关系是接口与实现类之间的关系。代码中表现为继承抽象类或者接口。

依赖关系

使用带箭头的虚线来表示。依赖关系是一种临时的关联关系，是对象之间耦合度最弱的一种关联方式，可能随着运行时的变化依赖关系也发生变化。表示一个类在运行过程中使用到了另一个类中的对象。

二、7大设计原则

2.1开闭原则

在扩展功能的时候选择创建而非修改的方式。这就要求在具体实现的地方使用更少的功能性的代码编写，而将这部分代码交给外部的方法。

2.2里氏代换原则

描述父类和子类之间的规范，即父类能使用的地方，子类一定可以使用，要求子类不能修改父类原有的功能（不重写方法）。这要求父类尽可能抽象，并且子类中方法的入参类型必须与父类中被覆写的方法的入参类型相同或更宽松。对应的是，有子类出现的地方，父类未必就可以代替，因为每个子类都可以具有个性。

Java中多态就是一个体现。？

2.3依赖倒转原则

高层模块不应该依赖底层模块，两者都应该依赖其抽象；抽象不应该依赖于细节，细节应该依赖抽象。对抽象进行编程，而不是对实现进行编程。

面相接口编程，模块间的依赖通过抽象发生，实现类之间不直接发生依赖关系，而是接口或抽象类产生

2.4接口隔离原则

对接口进行规范

2.5迪米特法则

最少知识原则，和‘朋友’直接交谈，不和陌生人说话。朋友之间的关系也不能太过亲密。

2.6合成复用原则

尽量适合组合或者聚合等关联关系来实现，其次使用继承。

维护类的封装性，降低对象的耦合度，复用的灵活性高。

2.7单一职责原则

对完整的业务进行拆分，按照共性划分设计接口，达到单一职责。

3.1创建型模式

3.1.1单例模式

懒汉模式

懒汉模式通过使用synchronized和volatile关键字的方式来保证创建对象的单例。synchronized对方法加锁，volatile保证instance创建的可见性，避免指令重排的发生。代码对加锁的方式进行了优化。

饿汉模式

饿汉模式使用的JVM中的类加载机制实现单例，静态对象初始化的时候创建一次，后续返回的都是该对象。

静态内部类

静态内部类同样是使用JVM类加载的机制实现单例，相较于饿汉模式，静态内部类的方式将对象创建放到了静态内部类中，只有当需要用到instance的时候才会创建该对象，实现了懒加载。

反射对单例的破坏

通过反射创建的对象后，无法保证单例模式。

对于饿汉模式和静态内部类，可以在私有的构造函数添加判断来阻止反射创建新的对象，但是在懒汉模式中无法阻止。

经过尝试，懒汉模式也可以实现阻止反射创建新对象，但是在instance已经被创建之后。

反射创建对象是通过直接调用构造函数的，在懒汉模式中，反射不会在创建对象前判断对象并不会对类中的静态变量instance产生影响，所以产生两种情况1.先反射创建，然后getInstance创建；2.先getInstance创建，然后反射创建；

结果不同：

  • 情况1：创建了两个不同的对象
  • 情况2：阻止了反射创建新对象

在懒汉模式中，对象并没有提前创建，所以在构造函数中获取不到单例对象的判断（还没有创建），因此单例被破坏。

在饿汉模式和静态内部类中，均在类/变量加载的时候对静态变量初始化了，因此反射在用构造函数创建对象的时候对Instance!=null的判断为true。

对于静态内部类的懒加载，事实证明，JVM对内部静态类的处理方式不同。它们保持隐藏，直到实际使用时才初始化实例对象。Java 中懒加载的正确实现方式_java懒加载-CSDN博客

Enum枚举类实现单例

使用枚举实现的方式是可以防止反射创建对象，同时也由JVM保证它是线程安全的。

反序列化对单例的破坏

从返回结果可以看出，反序列化后的对象和创建的单例对象不一致，即破坏了单例，这是因为反序列化并不会走构造函数。在Serializable接口中，提供了解决方法，通过serialVersionUID和实现readResolve()方法来解决。

在对象的比较中，对比的是UID，即使在类中有修改，对之前序列化也是认为与修改后的类相同。

在枚举类型enum中是支持反序列化操作的，且单例不会被反序列破坏。

简单工厂模式

简单工厂存在的问题与解决方法： 简单工厂模式有一个问题就是，类的创建依赖工厂类，也就是说，如果想要拓展程序，必须对工厂类进行修改，这**违背了开闭原则**，所以，从设计角度考虑，有一定的问题，如何解决？我们可以定义一个创建对象的抽象方法并创建多个不同的工厂类实现该抽象方法，这样一旦需要增加新的功能，直接增加新的工厂类就可以了，不需要修改之前的代码。

总结，简单工厂模式对类的创建依赖于工厂类，所以在扩展的时候会对工厂类进行修改；

工厂方法模式对创建对象的方法进行抽象，实际工厂类继承该抽象（工厂抽象可以满足单一职责原则，即创建工厂），这样在对工厂类添加扩展只需要创建一个新的工厂类就可以了；

  • 简单工厂模式是不符合开闭原则，因为增加产品会对原本的工厂进行修改。
  • 工厂方法模式是符合开闭原则，因为增加产品只需要再新增相应的工厂类就行，不需要修改原来的代码。
  • 抽象工厂模式既符合也不符合开闭原则。符合开闭原则时，因为增加一个新的产品族时（例如某农场负责的养鸡和种葡萄业务），只需要增加一个新的具体工厂，不需要修改源代码，满足开闭原则。但是当产品族中需要增加一个新的产品时（例如农场又提供衣服产品，如棉衣等具体产品）那么所有的工厂类都需要进行修改，此时不满足开闭原则。

另一方面，当系统中只存在一个等级结构的产品时，抽象工厂模式将退化至刂工厂方法模式。

3.2.5桥接模式

说明

桥接模式是一种很实用的结构型设计模式，如果软件系统中某个类存在两个独立变化的维度，通过该模式可以将这两个维度分离出来，使两者可以独立扩展，让系统更加符合“单一职责原则”。与多层继承方案不同，它将两个独立变化的维度设计为两个独立的继承等级结构，并且在抽象层建立一个抽象关联，该关联关系类似一条连接两个独立继承结构的桥，故名桥接模式。

桥接模式用一种巧妙的方式处理多层继承存在的问题，用**抽象关联取代了传统的多层继承，将类之间的静态继承关系转换为动态的对象组合关系**，使得系统更加灵活，并易于扩展，同时有效控制了系统中类的个数。

桥接定义如下： 桥接模式(Bridge Pattern)：将抽象部分与它的实现部分分离，使它们都可以独立地变化。它是一种对象结构型模式，又称为柄体(Handle and Body)模式或接口(Interface)模式。

总结

优点

  • 分离抽象接口及其实现部分。
  • 可以取代多层继承方案，是比多层继承方案更好的解决方法，极大减少 了子类的个数。
  • 桥接模式提高了系统的可扩展性，符合开闭原则。

缺点

  • 桥接模式的使用会增加系统的理解与设计难度，由于关联关系建立在抽象层，要求开发者一开始就针对抽象层进行设计与编程。
  • 桥接模式要求正确识别出系统中两个独立变化的维度，因此其使用范围具有一定的局限 性，如何正确识别两个独立维度也需要一定的经验积累。

适用场景

  • 如果一个系统需要在抽象化和具体化之间增加更多的灵活性，避免在两个层次之间建立静态的继承关系，通过桥接模式可以使它们在抽象层建立一个关联关系。
  • “抽象部分”和“实现部分”可以以继承的方式独立扩展而互不影响，在程序运行时可以动态 将一个抽象化子类的对象和一个实现化子类的对象进行组合，即系统需要对抽象化角色和实现化角色进行动态耦合。
  • 一个类存在两个（或多个）独立变化的维度，且这两个（或多个）维度都需要独立进行扩展。
  • 对于那些不希望使用继承或因为多层继承导致系统类的个数急剧增加的系统，桥接模式尤为适用。

在产品出现多个层级的划分时，需要考虑这些层级是否存在一种类似笛卡尔积的关系（新增一种产品或品牌导致多个类需要添加该新增），若存在，则可以考虑使用桥接的方式优化。

将每一功能的单一实现抽象出共有的方法或关系，然后将该方法或关系抽象出来，通过“桥”的抽象方法来连接具体功能的实现和实现的方法。例如微信支付是具体功能，而面容支付和指纹支付是实现方法，对于支付实现方法，可以抽象出一个接口，然后定义一个抽象类，即“桥”，来定义具体功能的抽象，其中调用支付实现抽象方法。

桥接的好处在于使用了一个“桥”类来实现两类对象的关联。

3.3行为型模式

行为型模式分为类行为模式和对象行为模式，前者采用继承机制来在类间分派行为，后者采用组合或聚合在对象间分配行为。由于组合关系或聚合关系比继承关系耦合度低，满足“合成复用原则”，所以对象行为模式比类行为模式具有更大的灵活性。

3.3.1策略模式

定义了一系列算法，并将每个算法封装起来，使它们可以互相替换，且算法的变化不会影响使用算法的客户。

抽象策略角色一般是通过**接口**来定义的，基于该接口实现不同的算法具体实现，他们之间可以相互替换。

3.3.2模板方法模式

通过抽象类实现，在抽象类中实现整体的流程的执行模板，例如登录、爬虫、输出这样一套模板，然后定义这些方法的抽象方法。然后基于不同的业务去继承这个抽象方法，分别实现其中的业务方法。

好处：开发者不需要关注业务的逻辑的流程，只需要针对功能进行开发。

‍

模板模式使用的是继承关系实现，策略模式使用的是组合关系实现。

策略模式具有状态后，成为了状态模式

定义： 状态模式实现了在一个类的内部状态改变后，可以令其行为也随之变化

适用场景： 一个对象 , 存在多个状态 , 状态可以相互转换 ; 不同状态下 , 行为不同 ;

优点： 不同状态隔离，表现为单独的类；状态转换的具体实现交由子类实现，减少相互依赖

缺点： 状态类管理问题

3.3.9访问者模式

通过将数据结构与操作分离，使得可以在不修改元素类的情况下，动态地添加新的操作。它适用于需要对复杂对象结构（文档，包含图片、文字）执行多种不相关操作（压缩，文本提取等）的场景，但需要注意其可能带来的复杂性和封装性问题。

对象结构并不提供具体的操作实现，而是通过一个方法，传入访问者实现功能扩展。有点类似抽象工厂的实现。

有类似于组合模式，将不同对象抽象为相同的类型（例如将文本、图片都抽象为DocumentElement），然后对这些对象执行统一的操作（visitor）【具体操作不需要对对象的类型进行条件判断，即一视同仁】。

3.3.11解释器模式

当需要解释执行某种语言,并且可以将语言中的句子表示为**抽象语法树(AST)** 时,解释器模式可以很好地处理这个问题。它通过定义语法规则和解释规则,将各个表达式节点组织成树形结构,然后递归地解释执行。
